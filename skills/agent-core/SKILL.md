# Agent Core

- Treat credentials as secrets stored in the user's configured credential provider, such as a password manager. Retrieve them only when needed; never store them in source control, plugin files, notes, chat, logs, or command output.
- Use existing secure authentication when available. Pass secrets through supported secure mechanisms instead of displaying or embedding them.
- For access questions, follow the service's authentication guidance and reuse its intended account's native login first. When stored credentials are needed, identify and use an available credential-provider tool or skill before asking the user to supply them or reporting access unavailable. Do not insert password-manager discovery ahead of a service's supported OAuth/device-code setup.
- When a service skill publishes a credential contract and a credential-provider skill offers a compatible runner, use that public fast path as one operation instead of manually listing stores, inspecting fields, or reconstructing secret injection. Fall back to ordinary discovery when the fast path is unavailable, finds no match, or reports a genuine ambiguity.
- If that runner reports that provider authentication is required and the service consumer was not launched, report the required provider login and stop unless another already-configured direct credential source is known. Do not start speculative connector, environment, repository, or UI searches.
- Match the effort to the request. For a simple read-only access or identity check, take the shortest safe path and stop once it succeeds; do not inventory unrelated access methods or add redundant verification.
- Choose the best available access method for the task; purpose-built connectors, MCP tools, APIs, CLI commands, and SSH are options, not a fixed priority order. Before starting graphical-interface automation, briefly check the obvious available direct interfaces and prefer suitable structured access based on capability, reliability, security, and fidelity. Do not turn this into an exhaustive tool inventory or delay a simple task with speculative discovery.
- If the best in-scope approach requires a runtime, tool, or library, first reuse a compatible one already supplied by the host, workspace, or project. If it is genuinely absent, install a trusted, compatible version through the project's existing package manager or an isolated environment instead of silently switching to an inferior workaround.
- When that chosen approach is blocked by a missing or broken local prerequisite or non-secret configuration, make the smallest safe repair and retry once if the operation did not start; verify the outcome before repeating an uncertain mutation. Do not silently switch to an inferior route. Treat genuine authentication, authorization, remote-service, validation, and production-state failures according to their own recovery requirements instead of guessing or broadly changing local configuration.
- Prefer project-local or temporary installs outside cloud-sync roots; apply the storage guidance below before choosing an install location. Ask first only when installation requires administrator privileges, changes shared or production state, creates material cost, or has unclear trust or risk; otherwise install, verify, and continue.
- Use the graphical interface when the task is inherently visual or UI-specific, the user requests it, or no suitable direct interface is available. When browser interaction is needed, prefer a supported browser connection that controls the actual Chrome or Edge session over generic whole-computer control when it can perform the task faithfully, especially when existing browser login or extension state matters. Use generic computer control for native desktop applications, unsupported browser interactions, or when no suitable browser connection is available.
- Before making changes, confirm the intended account, tenant, project, database, and environment as applicable. Make the smallest appropriate change and verify the result.

## Cloud-synced project folders

- Before installing dependencies, cloning repositories, running tools that generate files, or starting a service, determine whether the working directory and intended write locations are cloud-synced. This applies across operating systems and providers, including OneDrive, iCloud Drive, Dropbox, Google Drive, and other cloud-sync or cloud-backup folders. Check resolved paths, redirected folders, and known sync roots; Desktop, Documents, a temporary-looking folder name, or a symlink does not establish that a location is local-only. Use bounded checks rather than scanning an entire cloud drive. When sync status is uncertain, choose a verified unsynced location for generated state.
- Reserve synced folders for durable material intentionally shared between devices: working documents, selected source files and inputs, final deliverables, dependency manifests and lockfiles, setup instructions, and completed backup snapshots. Judge suitability by purpose, reproducibility, file count, and write frequency as well as size. A small dependency tree can create more sync work than a large finished document.
- Do not create or run machine-specific or high-churn working state inside a sync root: installed dependencies and virtual environments, package/download/model caches, build and test intermediates, disposable source snapshots, continuous logs or traces, browser profiles, live databases and journals, application state, container storage, or virtual-machine disks. These are examples of a general storage rule, not a provider-specific filename blacklist. A required deliverable such as a test report, source archive, or database export may be copied in once complete; its live working directory belongs outside sync.
- Keep active repository clones, Git metadata, and worktrees outside synced folders. Use version control to exchange committed code, and preserve uncommitted work separately when needed. Do not create repeated repository copies under synced `tmp`, `outputs`, or similarly named directories just because the current project lives there.
- Reuse a suitable local workspace or choose a task-specific directory outside all known sync roots before generating files. Configure dependency, cache, build, log, and data paths there. If a tool requires its environment inside the project, run it from a local working checkout and copy back only the intended documents or deliverables. Use task-scoped settings rather than changing global tool configuration or disabling cloud sync for unrelated work.
- When the host supports multiple project folders, add the local working directory to the existing project as a secondary folder through the host's supported project settings or API. In Codex, keep the existing primary folder and append the local folder without replacing other roots, creating a duplicate project, or changing the primary folder unless requested. Verify the saved folder list and access to the local directory. If folder management is unavailable, report the exact folder to add and continue authorized work there; do not claim it is attached or edit internal application state as a substitute.
- A secondary folder does not change a task's working directory or guarantee automatic discovery of its instructions and configuration. Run commands with the intended local working directory explicitly, read applicable instructions there, and check effective tool configuration and write paths. In Codex, the primary folder controls default task and Git context and automatic instruction discovery. Keep a brief handover note in the primary folder identifying the local workspace and recreation steps, so future tasks and other computers can resume without relying on an unrecorded machine-specific path.
- Do not assume `.gitignore`, hidden files, `.nosync` naming, or symlinks exclude content from cloud sync. Treat an exclusion as effective only when the provider supports it and it is verified for the actual path; otherwise use a directory outside the sync root. A local path that resolves back into synced storage does not provide isolation.
- Preserve portability through setup commands, dependency versions, source revisions, relative paths, and brief handover notes explaining how to recreate local state. Transfer databases through consistent, completed exports or backups. Keep credentials in their credential provider. Do not rely on copying a live environment or database directory between computers to resume work.
- For an existing synced project, route new scratch work outside sync first. Move or remove existing content only within the authorized task, after accounting for valuable outputs, cloud-only files, uncommitted changes, linked worktrees, and references from running tools or other tasks. Verify that retained content is available and usable before removing an old copy; never infer that a folder is disposable solely from its name.
- Verify the effective write locations before a substantial run and check that generated state stays outside sync. Report the local working location and the durable files retained in the synced project. Clean up task-owned temporary state when no longer needed, using managed lifecycle tools where available, while preserving work still in use.
