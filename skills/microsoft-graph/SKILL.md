# Microsoft Graph

- Use Microsoft Graph for supported Microsoft cloud work, including Outlook, Microsoft 365, Entra, Intune, files, collaboration, reports, and security. Graph is not Azure resource management and does not replace service-specific administration where Graph lacks the capability.

## Accounts and authentication

- Use the current official Microsoft Graph PowerShell SDK in PowerShell 7.2 or newer, with `Microsoft.Graph.Authentication` 2.37.0 or newer. If it is absent or older, install or update it for the current user.
- For delegated device-code sign-in, run `scripts/connect_graph.ps1`, resolved relative to this skill directory, with the intended account, tenant, environment, and scopes. Keep the helper and the following Graph cmdlets or `Invoke-MgGraphRequest` calls in the same PowerShell process. The helper only authenticates and connects the ordinary Graph PowerShell SDK; it does not limit which Graph operations the agent can perform.
- The helper first reuses a verified matching SDK-managed session already active in that PowerShell process. Otherwise it uses Microsoft's public OAuth device-code and refresh-token endpoints, then supplies a verified access token to the ordinary SDK. It never disconnects another account or deletes saved authorization to switch accounts. `-ForceDeviceCode` deliberately starts a fresh device flow while retaining existing saved tokens until the new account is verified.
- Refresh tokens are separated by account, tenant, and cloud: Windows uses current-user DPAPI (including the existing helper's cache), macOS uses Keychain, and Linux requires `secret-tool`/libsecret with an unlocked Secret Service session. A locked, unavailable, or unreadable store is a local prerequisite failure; repair it before retrying, without starting repeated sign-ins. No tokens are passed in native process arguments or stored as plaintext files.
- A new PowerShell process may have no active SDK context even when the SDK has a persistent login. The helper does not inspect or modify that private cache, or start interactive SDK login to guess its account. Such an existing Mac/Linux account may require one device-code migration into the account-specific OS store; the old SDK cache remains intact. An already active matching SDK session continues using native automatic refresh.
- Target the account, tenant, and cloud explicitly. Use the same tenant identifier on later calls; aliases and GUIDs intentionally produce separate cache keys. On first use, show one device code and wait for that attempt to finish. The helper verifies `/me` before saving or connecting a newly acquired token. Device polling follows Microsoft's returned `expires_in`; the SDK's separate 120-second client timeout is not a code-expiry or permission-rejection signal.
- Retain the returned connection metadata. `Authentication=ProvidedToken` means the SDK cannot refresh that token itself: rerun the helper with the same account, tenant, cloud, and scopes at `RefreshAfterUtc` or before the next batch of work to refresh silently and reconnect. Never replay a mutation whose outcome is uncertain merely because authentication expired. `Authentication=SdkManaged` retains native SDK refresh.
- `ScopeVerification=Unavailable` means the provider did not expose granted-scope metadata; it does not mean consent was denied. This can occur with opaque personal-account tokens. Verify permissions needed by the requested operation independently and do not claim broad permission setup is complete from unknown metadata.
- Keep initial permission setup separate from ordinary use. For setup, preserve the user's preference for maximum compatible delegated access unless narrower access was requested. Build a non-secret account-specific plan of requested, granted, and pending scopes using current [Microsoft permission information and consent limits](https://learn.microsoft.com/en-us/graph/permissions-overview). Exclude application-only, account-incompatible, obsolete, separately configured resource-specific, and redundant permissions; prefer a management scope where it subsumes a read scope.
- Validate the plan before consent and respect the actual client's audience and request-size limits. Request the broadest valid compatible bundle within those limits; split setup into additional consent batches when a limit requires it. A size limit does not make every permission in a bundle invalid. Diagnose timeout, invalid scope, missing consent, conditional access, and unsupported API separately, and remove only permissions shown to be invalid or incompatible. Broad setup can require administrator approval and cannot guarantee one consent covers every future capability.
- Compare known granted scopes with the plan and identify pending administrator consent or unavailable capabilities. Ordinary authorized work can continue with sufficient permissions while broader setup remains pending. Do not report the broad setup complete while required compatible grants remain missing or unverified.
- Use delegated authentication for work performed as a person. App-only authentication is a separate setup for explicitly unattended or tenant-wide work.
- Never expose, print, persist manually, or place tokens and refresh material in plugin files, source control, chat, notes, command arguments, or logs. Each device authenticates its own accounts, and the helper handles any local protected token material.

## Requests

- Prefer direct structured Graph access over UI automation when Graph supports the task. Let the AI choose the suitable official PowerShell cmdlet or Graph request for the operation; this skill is guidance, not an operation allowlist.
- Default to the stable `v1.0` endpoint. Use `beta` only when the required feature is unavailable in `v1.0`, and tell the user when relying on beta behavior.
- Follow `@odata.nextLink` when the complete result set is required. Respect Graph throttling and `Retry-After`; retry only safe operations automatically and do not blindly replay a mutation whose outcome is uncertain.
- For shared or delegated Outlook resources, use the account that holds permission and address the target mailbox or calendar explicitly. Do not mistake a shared mailbox for another authenticated account.
- For Teams chats and channel replies, read the recent conversation and continue naturally without redundant greetings or repeated updates. Omit routine email-style sign-offs and signatures such as "Kind regards, Name" or "Thanks, Name", even in the first message, unless explicitly requested by the user. A natural thank-you in the message itself is fine. Preserve explicitly requested wording; these chat conventions do not apply to email correspondence.
- Never send, reply to, or forward email without first showing the user a complete preview containing the sending account, To, Cc, Bcc, subject, body, and attachments, then receiving explicit confirmation to send. If any of those details change, show the updated preview and confirm again. Creating or editing a draft is not authorization to send it.
- Before changing calendar entries, modifying files, or performing administrative actions, confirm the intended account and target from available context. Verify every external change, including a confirmed email send, and report the result.
