# Microsoft Graph

- Use Microsoft Graph for supported Microsoft cloud data and operations, including Outlook mail, calendars, contacts, OneDrive and SharePoint files, Teams, To Do, Planner, OneNote, Excel, Bookings, users, groups, Entra, Intune, reports, and security data. Check the current Graph documentation when endpoint behavior or coverage matters.
- Do not treat Graph as Azure resource management, Power Platform, or a complete replacement for Exchange, Teams, SharePoint, or Purview administrative PowerShell. Use Graph when it exposes the required capability; otherwise use the appropriate Microsoft service tool.

## Accounts and authentication

- Treat multi-account use as the default design. Every Graph operation must target an explicit Microsoft identity and, when relevant, tenant. Never silently use whichever account authenticated most recently.
- Prefer the account or alias named by the user. If the intended account cannot be determined safely from the request or known non-secret profile metadata, ask which account to use before accessing data or making a change.
- For portable terminal access, prefer `scripts/graph_request.ps1`. It calls Microsoft Graph directly and uses Microsoft's MSAL device-login flow, verifies the resulting identity, and keeps a separate OS-encrypted token cache for each account. It does not use Windows Account Manager or the Graph PowerShell authentication/request layer.
- The helper uses pinned official `@azure/msal-node` and `@azure/msal-node-extensions` packages. On first use it installs them into its user-state directory with an available npm or pnpm supplied by the user or host, verifies the native secure-cache component, and relies on DPAPI on Windows, Keychain on macOS, or LibSecret on Linux; it never enables a plaintext token-cache fallback.
- On first use of an account, give the displayed code to the user once and wait for the same process to finish. Do not start another sign-in merely because the browser already reports success. If the command itself fails, stop and diagnose it rather than issuing repeated codes. Later calls should silently reuse and refresh the encrypted account cache; use `-ForceSignIn` only when the user asks to replace that account's saved authentication.
- Device login does not select an account from the email argument. The user chooses the identity on Microsoft's page; the helper then rejects a different identity instead of saving it under the requested account.
- A Microsoft account can return a canonical sign-in identity that differs from the alias the user named. If that happens, do not issue repeated codes. Ask once whether the returned identity is the same account; if confirmed, rerun using the canonical identity so future cache lookups are reliable.
- Use delegated authentication for work performed as a person. Use app-only authentication only for an explicitly configured unattended or tenant-wide workflow. Do not create an app registration, client secret, certificate, or broad admin consent merely to avoid an ordinary delegated sign-in.
- When adding or authenticating an account, use one broad device-code consent by default so later Graph tasks do not repeatedly ask for permissions. Ask only whether the identity is work/school or personal when that is not already clear, warn once that maximum access is intentionally broad, then use `-AccessProfile MaximumWorkOrSchool` or `-AccessProfile MaximumPersonal`. These profiles request a maintained set of the broadest non-redundant delegated permissions that Microsoft accepts in one device-code request; the work/school profile includes Outlook and shared mailboxes, files and collaboration, directory administration, Intune and devices, security, compliance, and related Graph services. Give the user exactly one code and wait for that process. Never expand the request to every published Graph scope and never split ordinary account setup into multiple consent codes. Some work/school permissions require administrator approval and suitable directory roles; if Microsoft denies them, report that account or tenant restriction instead of silently falling back to repeated sign-ins. Later calls should request only the scopes needed by the operation and silently reuse the broad consent already held in the encrypted cache. If Microsoft or an administrator later revokes consent, changes policy, or adds a new permission, further interaction may still be unavoidable.
- Application permissions are not available to a signed-in account and therefore cannot be included in account authentication. Operations requiring application permissions need a separate tenant-owned Entra app registration, administrator consent, and secure app credential; never claim that an interactive user token has application permissions or embed a shared app credential in this public plugin.
- Tokens and refresh material belong only in the official secure local cache or another configured credential provider. Never place them in plugin files, source control, chat, notes, command arguments, logs, or output. The plugin contains no account or authentication state; each device authenticates its own accounts.

## Requests

- Prefer direct structured Graph access over UI automation when Graph supports the task. Use an existing suitable Graph connector, the official Graph PowerShell SDK, a Graph SDK, or REST according to the task; there is no fixed priority among capable direct tools.
- Let the helper discover a compatible host-supplied Node.js and npm or pnpm runtime and complete its own first-use setup. If no compatible runtime exists, install Node.js 20 or later in the current user's scope and retry instead of switching to browser automation. Do not manually repair the helper's package directory or substitute Graph PowerShell authentication for this helper on Windows.
- For routine JSON REST calls, prefer `scripts/graph_request.ps1`. It accepts any Graph URI, standard HTTP method, scopes, headers, and JSON body, verifies the selected account, and returns the Graph response. It is an optional transport shortcut, not an operation allowlist. Bypass it for binary transfers, large uploads, batching, subscriptions, specialized SDK behavior, or any task another direct tool handles better.
- Resolve the helper relative to this skill directory. Initial work/school setup is `pwsh -NoProfile -File scripts/graph_request.ps1 -Account <ACCOUNT> -Method GET -Uri '/v1.0/me' -Scopes User.Read -AccessProfile MaximumWorkOrSchool`; use `MaximumPersonal` for a personal Microsoft account. A later task-specific access check can omit `-AccessProfile` and pass only its required scopes. Other optional parameters are `-TenantId`, `-Environment`, `-BodyJson`, `-HeadersJson`, `-OutputFilePath`, and `-ForceSignIn`; do not run a help command first.
- Default to the stable `v1.0` endpoint. Use `beta` only when the required feature is unavailable in `v1.0`, and tell the user when relying on beta behavior.
- Follow `@odata.nextLink` when the complete result set is required. Respect Graph throttling and `Retry-After`; retry only safe operations automatically and do not blindly replay a mutation whose outcome is uncertain.
- For shared or delegated Outlook resources, use the account that holds permission and address the target mailbox or calendar explicitly. Do not mistake a shared mailbox for another authenticated account.
- Before sending mail, changing calendar entries, modifying files, or performing administrative actions, confirm the intended account and target from available context and verify the result after the change.
